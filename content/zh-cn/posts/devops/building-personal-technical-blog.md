## 引言

这个网站是我的个人技术博客，也是本站第一篇文章的主题。在 2026 年 8 月底开始这个项目时，我希望它不只是发表文章的地方。博客的定位还包括：

- 可以持续复用和扩展的技术知识库。
- 展示工作方式的云 / DevOps 工程作品集。
- 记录工程决策与经验教训的地方。
- 将现代开发与自动化实践应用在一个小而真实的项目上的具体示例。

本文介绍这个网站背后的工程思路：需求、技术选型、分阶段实施，以及现在负责验证与部署的自动化体系。

## 为什么要把它当作工程项目来构建？

核心决策是：把博客当作一个小型工程项目来对待，而不是直接安装一个博客平台然后开始写作。博客平台让发布变得简单，但也把大部分运维与架构决策从我手中拿走——而这正是我想在这个网站上练习的东西。

把它当作工程项目，并不意味着把它当作生产基础设施。这个项目的范围是个人网站，目标刻意保持适度。关键在于应用同样的习惯：

- **基础设施即代码的思路** —— 站点的配置与内容都是仓库中的声明式文件。
- **版本控制** —— 每一次变更都是一个可审查的提交，历史清晰。
- **可复现构建** —— 固定 Hugo 版本，主题作为模块依赖固定版本。
- **自动化验证** —— 变更合并前先运行 lint 与构建检查。
- **CI/CD** —— 验证、构建与部署都是自动化的，而不是手工操作。
- **增量实施** —— 工作拆分为可独立审查与验证的小阶段。
- **文档化** —— 写作、维护与部署流程都记录在仓库中。
- **可维护性** —— 依赖与工具保持精简，让站点运营成本低、变更容易。

## 需求与目标

架构来自一组明确的需求：

- 基于 Markdown 写作，内容保持纯文本且易于 diff。
- 静态站点生成，站点是待托管的一组文件，而不是需要运行的服务器。
- 基于 Git 的内容管理，仓库是唯一事实来源。
- 低成本运营与简单的托管方式。
- 通过现有 CI 自动化部署。
- 主题可维护，主题升级不会变成一个项目。
- 专业的技术呈现，包括代码高亮、搜索、深色模式与整洁的列表页。
- 支持文章中的技术示意图与代码示例。
- 为后续演进为作品集留出空间。

一些常见的"个人博客"配置一开始就明确不属于需求：自定义域名、评论、分析、新闻通讯或简历页面。它们在仓库中被记录为暂缓事项，而不是半成品实现，因为每一项都会增加运维成本。把需求当成一份刻意的清单，让后续决策——尤其是自动化投入在哪里——变得容易得多。

## 架构

架构刻意保持简单：开发者向 GitHub 推送内容，GitHub Actions 负责验证与构建，GitHub Pages 提供生成后的文件。

```text
Developer
    |
    | Git Push
    v
GitHub Repository
    |
    v
GitHub Actions
    |
    +--> Quality Gates
    |
    +--> Hugo Production Build
    |
    v
GitHub Pages
    |
    v
Personal Technical Blog
```

仓库是唯一事实来源：内容、配置与工作流定义都保存在 Git 中。GitHub Actions 是唯一的自动化层。质量门禁在 pull request 上运行；生产构建在 main 分支上运行；构建产物 `public/` 目录作为 Pages artifact 上传并部署。没有数据库，没有应用服务器，也没有第三方构建服务。

当前仓库不使用 Mermaid 图。在引入 Mermaid 之前，必须先在本地与生产环境验证其渲染，因此本文使用 ASCII 图；Mermaid 支持属于计划中的后续工作。

## 技术选型

### Hugo

Hugo 是一个静态站点生成器：它将 Markdown 内容与配置转换为一组 HTML 文件。它直接满足需求——基于 Markdown 写作、本地预览构建快、运维复杂度低。本项目使用 [Hugo Extended](https://gohugo.io/) `0.165.0`，记录在 `.hugo-version` 中，并在 CI 工作流中固定版本。

### Blowfish

Blowfish 是本项目的主题。选择它的主要原因：它面向以内容为中心的个人站点，维护活跃，并且开箱即用地提供了本项目所需的功能——个人主页、列表与卡片布局、搜索、深色模式、代码复制、分类体系与无障碍选项。主题以 Hugo 模块形式集成，在 `go.mod`/`go.sum` 中固定为 [v3.4.0](https://blowfish.page/)，因此升级是一次版本变更，而不是打补丁。自定义内容保持在站点配置与小型覆盖中，而不是直接修改主题文件。

### GitHub

GitHub 是协作与自动化中心。仓库保存一切，pull request 是内容与配置变更的审查机制，GitHub Actions 与审查发生在同一处。项目恰好位于 GitHub Pages 默认用户站点地址下，集成因此非常自然。源代码仓库是 [camillehe1992/camillehe1992.github.io](https://github.com/camillehe1992/camillehe1992.github.io)。

### GitHub Pages

GitHub Pages 在默认用户站点地址 <https://camillehe1992.github.io/> 提供站点。它是静态托管，运维开销非常低：无需管理服务器，公共用户站点的托管免费。一个重要的细节是部署方式：Pages Source 设置为 GitHub Actions，发布通过 CI 使用 OpenID Connect（OIDC）上传的已验证 artifact 完成，而不是基于分支发布。只有生产构建出的 `public/` 目录会被上传。

### GitHub Actions

GitHub Actions 提供验证、构建与部署流水线。pull request 运行质量门禁，推送到 `main` 的变更会被验证，Pages artifact 从 `main` 构建并部署。工作流使用所需的最小权限范围（`contents`、`pages`、`id-token`），并通过并发控制防止旧部署与新部署竞争。

### AI 编码助手

在整个项目中，AI 编码助手被用作实现辅助工具。它帮助搭建初始结构、产出配置与文档草稿，并按阶段实现小而定义清晰的任务。重要的边界是：AI 被用作实现与生产力工具，而架构、范围与工程决策始终由人工审查。它的输出与其他贡献一样被对待——必须经过审查、验证，并走正常的 Git 提交流程。项目刻意采用增量实现，就是为了让 AI 生成的变更足够小、便于审查。

## 分阶段实施策略

实施被拆分为十个阶段。下面的阶段列表是主要的实施结构：它有 Git 历史作为支撑，但阶段边界并不与提交或 pull request 一一对应。每个阶段都有清晰的目标，之所以单独划分，是为了能够独立审查与验证，并且每个阶段都有可核验的产出。

### 阶段 1 — 项目初始化

- **目标：** 在构建任何东西之前，先创建仓库骨架并记录计划。
- **为什么单独划分：** 脚手架与计划不应与实现混在一起；它为项目提供版本控制与明确的起点。
- **主要产出：** 初始化仓库，包含 `.editorconfig`、`.gitignore`、README，以及站点的空目录结构（`archetypes/`、`assets/`、`config/`、`content/`、`data/`、`layouts/`、`static/`）。

### 阶段 2 — Hugo 核心搭建

- **目标：** 让一个最小 Hugo 站点在本地构建成功。
- **为什么单独划分：** 在引入主题之前，先确认工具链可用。
- **主要产出：** 完成 Hugo 项目搭建，Hugo Extended `0.165.0` 记录在 `.hugo-version` 中。

### 阶段 3 — Blowfish 主题集成

- **目标：** 用维护中的主题替换手写的模板。
- **为什么单独划分：** 主题集成会改变站点结构，应与内容工作隔离。
- **主要产出：** Blowfish v3.4.0 以 Hugo 模块形式集成并固定于 `go.mod`/`go.sum`，临时的自定义布局被移除。

### 阶段 4 — 站点配置与个人品牌

- **目标：** 把站点配置成个人主页，而不是一个裸 Hugo 站点。
- **为什么单独划分：** 品牌与导航决策会影响之后的一切。
- **主要产出：** 站点基础配置（`hugo.yaml`、`params.yaml`、语言与菜单文件）、个人主页，以及 首页/文章/项目/关于 导航。

### 阶段 5 — 内容结构与写作流程

- **目标：** 定义文章的创建、格式与审查方式。
- **为什么单独划分：** 在第一篇文章出现之前，就需要统一的内容规范。
- **主要产出：** 文章 archetype（`archetypes/posts.md`）、`content/posts/` 下各主题的 `_index.md` 页面（aws、terraform、cloudformation、devops、security、ai），以及记录 front matter、图片、格式与发布流程的内容指南。

### 阶段 6 — GitHub Actions CI 验证

- **目标：** 在变更合并前验证站点。
- **为什么单独划分：** 验证应该在内容与配置积累之前就位。
- **主要产出：** pull request 与 main 分支工作流，运行 Hugo 生产构建（`hugo --minify --panicOnWarning`）。

### 阶段 7 — GitHub Pages 部署

- **目标：** 自动化发布。
- **为什么单独划分：** 部署是交付边界；自动化部署意味着每次合并都可能是一次发布。
- **主要产出：** 部署工作流，配置 GitHub Pages、上传构建产物 `public/` 目录，并通过 OIDC 在 `github-pages` 环境下部署。

### 阶段 8 — 质量自动化与验证

- **目标：** 把验证从单一构建扩展为一组质量门禁。
- **为什么单独划分：** lint 与链接检查能发现构建发现不了的问题，而且它们应该在 CI 中运行，而不只是在本地。
- **主要产出：** 共享质量脚本（`.github/scripts/validate-quality.sh`）运行 Markdown lint、YAML lint、GitHub Actions 语法检查、Hugo 生产构建与生成站点链接检查，并配套 lint 与 pre-commit 配置。

### 阶段 9 — 专业作品集增强

- **目标：** 让站点呈现为可信的工程作品集，而不只是博客。
- **为什么单独划分：** 作品集呈现需要对内容结构做设计决策，而不是继续加脚手架。
- **主要产出：** 带作者头像的个人主页、采用诚实案例研究规范与占位符的关于与项目页面，以及 `docs/superpowers/` 下的设计与计划文档。

### 阶段 10 — 多语言支持

- **目标：** 同时以英文与简体中文发布内容。
- **为什么单独划分：** 按语言拆分的内容布局与导航变更，不应与首批文章的写作混在一起。
- **主要产出：** Hugo 多语言配置（`languages.en.yaml` 与 `languages.zh-cn.yaml`）、相对路径一致的语言内容目录（`content/en/`、`content/zh-cn/`），使 Hugo 自动配对翻译，并新增简体中文菜单。

## 使用 AI 编码助手

项目采用增量方式实现，而不是让 AI 编码助手一步构建所有内容。形成的流程是：

1. **先规划。** 每项工作都从定义了目标与边界的书面计划或规格开始，而不是一个模糊的请求。
2. **维护清单。** 任务以明确条目跟踪，进度与剩余工作始终可见。
3. **一次只执行一个阶段。** 每个阶段都限定在一个小而可审查的变更范围内。
4. **审查 AI 生成的变更。** 助手的输出与其他贡献一样需要阅读与验证，绝不假设其正确。
5. **创建 Git 检查点。** 每个完成的部分单独提交，提供清晰的恢复点。
6. **继续前先验证。** 构建与质量检查在阶段边界运行，问题尽早暴露。

优势是务实的：脚手架、配置与文档草稿产出很快，小任务可以用精确的指令委派。局限同样务实：AI 输出需要验证，上下文必须显式移交，而且助手无法做项目级决策。让人工掌控架构、范围与工程决策是刻意的选择，而不是工作流的偶然结果。

## CI/CD 与质量门禁

概念上的交付流程是：

```text
Pull Request
    |
    v
Quality Gates
    |
    +--> Markdown lint
    +--> YAML lint
    +--> GitHub Actions syntax check
    +--> Hugo production build
    +--> Generated-site link check
    |
    v
Merge
    |
    v
Main
    |
    v
GitHub Pages Deployment
```

仓库中实际存在的检查：

- **Markdown lint** —— 通过 `npm run lint:markdown` 运行 `markdownlint-cli2`。
- **YAML lint** —— 对 `.github` 与 `config` 运行 `yamllint`。
- **GitHub Actions 语法** —— `actionlint`。
- **Hugo 生产构建** —— `hugo --minify --panicOnWarning`。
- **生成站点链接检查** —— 对构建后的 `public/` 目录运行 `linkinator`。

工作流：

- `.github/workflows/validate-pr.yml` 在 pull request 上运行质量门禁，并发布不含敏感信息的验证摘要。
- `.github/workflows/validate-main.yml` 在推送到 `main` 时构建站点。
- `.github/workflows/deploy-pages.yml` 构建生产站点，使用 `actions/configure-pages` 与 `actions/upload-pages-artifact` 上传 Pages artifact，并通过 `actions/deploy-pages` 使用 OIDC 与 `github-pages` 环境部署。

有一个区别值得说明：`npm run check:links`（对 README 与文档的 Markdown 链接检查）只是本地检查，不属于 CI。尚未实现的检查——例如拼写检查、密钥扫描、定时检查或 Lighthouse 审计——属于后续工作，不是当前的门禁。

## 经验教训

- **先规划再实现可以减少返工。** 简短的计划成本很低，但每个阶段一开始就有清晰的目标与边界，节省的时间远多于成本。
- **小阶段让 AI 辅助开发更容易审查。** 一次只涉及一个关注点的单提交变更可以快速验证；大而全的生成式 diff 做不到。
- **Git 提交提供有用的恢复点。** 每个阶段都以提交结束，因此随时可以检查、对比或回退某个具体步骤。
- **CI/CD 应该尽早引入。** 验证与部署工作流在第一篇文章之前就已就位，这意味着内容变更从一开始就自动接受检查。
- **主题与依赖管理应当按项目依赖对待。** 把 Blowfish 固定为 Hugo 模块并在仓库中记录 Hugo 版本，把"主题维护"从未知风险变成了例行版本变更。
- **个人网站是实用的工程沙盒。** 它小到可以快速变更，真实到必须诚实，又显眼到足以推动良好实践。

## 下一步计划

以下属于计划中的改进，而不是已实现的功能：

- **更多技术文章与项目案例。** 内容分区已就绪；项目分区在真实实现准备好分享之前仍保留占位符。
- **更好的作品集呈现。** 例如，手动为已发布的案例研究添加仓库链接，不引入 GitHub API 集成。
- **验证 Mermaid 渲染**，在本地与生产环境验证通过后再引入 Mermaid 图；本文因此使用 ASCII 图。
- **SEO 优化**与**自定义域名**，这两项因为会增加所有权与配置成本而被暂缓。
- **隐私友好的分析**，只有在价值足以抵消新增追踪时才引入。
- **更多质量自动化**，例如拼写检查、密钥扫描、定时检查与 Lighthouse 审计。
- **AI 辅助的内容工作流**，例如草稿审查与一致性检查，待手工流程得到验证后再引入。

## 结语

这个博客既是发布平台，也是一个持续演进的工程项目。它背后的基础设施刻意保持精简，自动化刻意提前，所有决策都记录在仓库中。本文是内容的开始，而不是项目的终点。
